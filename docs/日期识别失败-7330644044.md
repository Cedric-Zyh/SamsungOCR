# 7330644044.jpg 签收日期失败诊断（2026-09-18）

出库单 `7330644044.jpg`（2479×3609，广州花东DC仓库）在网页端以 `paddle_v6` 识别时，
「签收日期」阶段报：

```
OpenCV(4.10.0) .../imgcodecs/src/loadsave.cpp:1134:
error: (-215:Assertion failed) !image.empty() in function 'imencode'
```

线上记录（`storage/results.db`，`results.id = 3165`，2026-09-18T11:56）与复现一致：
`date_check.status = "识别失败"`，`date_ocr_texts` 为空。

这个问题有**两层**，第一层是 bug（已修），第二层是设计取舍（待决策）。

---

## 第一层：空裁剪图让整个日期阶段崩掉（已修）

### 触发链

```
stage_date.execute
└─ date_crops._recognize_receipt_date
   └─ date_crop_workflow.collect_date_regions      ← 依次处理 tight/wide/lower/far_lower/deep_lower
      └─ date_crop_preparation._prepare_date_region:17
         └─ image_processing.save_receipt_date_crop:697   _write_stage_image(raw_destination, crop, ".jpg")
            └─ image_processing._write_stage_image:734
               └─ cv2.imencode(...)  ← !image.empty() 断言
```

### 为什么是空的

各日期窗口都是**签章锚点的偏移**，锚点取「签章要求」行：`stage_date.py:40`
`signature_anchor = signature_row.y`。本单该行在 **y = 0.7362**（多数样本在 0.47～0.50 附近），
于是非紧裁窗口 `[anchor+shift+0.052, anchor+shift+0.112]` 逐级下滑：

| 区域 | shift | 纵向窗口（归一化） | 像素行 | 结果 |
|---|---:|---|---|---|
| tight | 0.00 | 0.804 ~ 0.844 | 2902 ~ 3046 | 正常 |
| wide | 0.00 | 0.788 ~ 0.848 | 2844 ~ 3061 | 正常 |
| lower | 0.055 | 0.843 ~ 0.903 | 3043 ~ 3259 | 正常 |
| **far_lower** | 0.23 | **1.018 ~ 1.000** | **3674 ~ 3609** | **空** |
| deep_lower | 0.31 | 1.098 ~ 1.000 | 3963 ~ 3609 | 空 |

`y2n` 被 `min(1.0, ...)` 截到页底，`y1n` 却没有上界，所以 `y1 > y2`，
`image[3674:3609]` 得到空数组。`save_receipt_date_crop` 里对 `crop` 没有任何面积检查，
第一个用到它的就是 `imencode`，于是抛出断言。

`far_lower` / `deep_lower` 是**审计用可选区域**（`audit_only=True`，证据被压在 0.35 置信度以下、
不参与自动放行）。本单页脚偏低，这两个窗口根本没有落脚位置，本应「没有证据」，
却让整个日期阶段失败，连正常裁剪已经读到的日期也一起丢掉。

### 修复

- `receipt_ocr/image_processing.py`：新增 `DateCropOutOfRange(ValueError)`；
  `save_receipt_date_crop` 在 `crop = image[y1:y2, x1:x2]` 之后检查 `crop.size == 0`
  并抛出它（消息里带上归一化窗口与图片尺寸，便于归因）。
- `receipt_ocr/date_crop_workflow.py`：`collect_date_regions` 捕获该异常后 `continue`。
  这与该循环既有语义一致——它本来就会静默跳过 `lower/far_lower/deep_lower`（日期已找到时）。
- 新增 `tests/test_date_crop_out_of_range.py`：越界窗口报错且不落盘、同一锚点下正常窗口不受影响、
  工作流跳过越界区域但其余区域照常处理、锚点偏高时 `deep_lower` 仍可达。

修复后同一张图日期阶段可以走完，产出 3 个区域（紧凑/宽/下方扩展）的证据图，状态从
`识别失败` 变成 `未识别`。

## 第二层：日期其实读对了，被位置门滤掉（已修）

**OCR 没问题。** 同一次运行里：

```
date_ocr_texts = ['2026年2月4日', '血早', '020n2026年2月4日', 'ZOOIL', '2026年2月4日',
                  '2026年2月4日', '3976年2月4日', '20%6年2月4日1', ...]
紧凑区域 OCR: '2026年2月4日' / '2026年2月4日'
宽区域   OCR: '206年2月4日' / '2026年2月4'
要求到货: 2026-02-04
```

读到的 `2026年2月4日` 与要求到货**完全一致**，本该判「匹配」，却判成「未识别」。

### 原因

`receipt_ocr/parsing_dates.py:86`，`find_receipt_date` 里有一个按**页面绝对比例**写死的位置门：

```python
# The receiving date is on the right side of the signature table.
if 0.50 <= row.y <= 0.69 and row.x >= 0.58:
    score = row.confidence + row.x + (0.2 if "年" in row.text else 0)
```

本单收货日期在 **y ≈ 0.814**（整页 OCR：`'6年2月4日'` y=0.814 x=0.869、`'202'` y=0.817），
整窗落在 0.50~0.69 之外，全部候选被丢弃。直接验证（同一文本、同一置信度，只改 y）：

```
y=0.814 x=0.869 -> (None, None)                    ← 本单实际位置
y=0.600 x=0.870 -> date(2026, 2, 4), 已接受
y=0.814 x=0.300 -> (None, None)
```

### 其它兜底路径也覆盖不到

- `_find_confirmed_far_lower_date` 要求 artifact 上有 `far_lower_cross_model_candidate` 标记，
  而该标记只在 `date_crop_region_output.py` 里 `ocr_backend == "vision" and
  secondary_ocr_backend == "paddle"` 时才会生成 —— `paddle_v6` 计划下永不产生。
- `_find_low_confidence_date_audit`（`date_audit_evidence.py:18`）按设计只收
  `confidence <= 0.35` 的审计候选；正常裁剪读到的高置信行进不去。
  （它的文档字符串本身就写着：`find_receipt_date` intentionally accepts only the
  normal footer band。）

于是 `decision.actual_date` 始终为 `None` → `compare_dates` 返回「未识别」。

### 修法：改参照物，不改宽度

量了 12 张真值样本的「签章要求行 → 收货日期行」垂直偏移：

| 样本 | 签章要求行 y | 日期行 y | 偏移 |
|---|---:|---:|---:|
| 7266702320 | 0.471 | 0.553 | +0.082 |
| 7266933626 | 0.470 | 0.554 | +0.084 |
| 7267130988 | 0.472 | 0.551 | +0.079 |
| 7267237228 | 0.470 | 0.553 | +0.083 |
| 7267446210 | 0.470 | 0.553 | +0.083 |
| **7330644044** | **0.736** | **0.814** | **+0.078** |

**偏移恒定 +0.078 ~ +0.084，无一例外**；变的只是页脚在页面上的高度。
也就是说 `0.50 ~ 0.69` 这个"绝对比例窗口"其实是**相对页脚的窗口被换算成了页面比例**——
对 `anchor ≈ 0.471` 的常规版式它等于 `anchor + 0.03 … anchor + 0.22`。
页脚一旦下移到 0.736，窗口就整体落空。**所以不是窗口太窄，是挂错了参照物。**

改动（`receipt_ocr/parsing_dates.py`）：

- 新增 `DATE_BAND_*` / `REFERENCE_ANCHOR_Y = 0.471` / `ANCHOR_OFFSET_TOP|BOTTOM` 常量，
  把上述测量结论写进代码注释；
- `find_receipt_date(rows, required_text, *, anchor_y=None)` 增加可选的锚点；
  命中条件变成 `旧绝对带 OR anchor 相对带`。
  **旧判断被完整保留为 OR 的一项，所以构造上不可能丢掉任何现在能收的行**，
  唯一的变化是"新收进来的"。
- 只有知道锚点的调用方传参：`stage_date` → `DateStageEvidence.anchor_y` →
  `date_selection._select_complete_dates`。其余调用点（存量证据审计、裁剪工作流的提前退出）
  不传，行为逐字不变。

### 修复后的实际结果

```
status      : 匹配
actual      : 2026-02-04
confidence  : 0.68            ← 被安全规则压到此值
reliable    : False
safety_policy: 单一 Paddle 模型安全模式：日期和印章保留候选，但必须人工复核
```

对界面意味着：

- 复核面板「识别到的签收日期」由 **未识别** 变为 **2026-02-04**；记录列表的日期核对也随
  `status` 变为匹配。
- 但 `reliable === False`，而 `review.mjs` 的 `autoConfirmed` 与 `records.mjs` 的
  `canBulkConfirm` 都要求 `status === '匹配' && reliable === true`，
  所以它**不会被自动确认，也进不了「批量确认通过」**，必须人工确认。
  这正是"日期作为候选呈现、由人拍板"的语义。

### 验证

- 新增 `tests/test_parser.py`：低页脚版式必须命中、锚点带是绝对带的超集（多锚点遍历）、
  页脚下方过远 / 左侧 / 页脚上方仍必须拒绝。
- 整轮套件：**2 failed, 958 passed**（两个失败是既有的 `test_frontend_behavior.py` 漂移，
  与本改动无关）。日期/分析器子集：**431 passed**。

### 仍需注意的一点

`_apply_single_paddle_safety` 只在「page/date/seal 三个阶段都是 Paddle」时生效。
`paddle_v6`（本次出问题时的选择）满足该条件，新收进来的日期必然被压成人工复核，无风险；
而 `hybrid`（macOS 默认）路由为 `{page: paddle, date: vision, seal: vision}`，
三个阶段不是同一个模型，**该安全规则不生效**，新收进来的低页脚日期有可能被判为可靠。
若要覆盖 `hybrid`，应先用 301 条真值跑一遍 A/B 再决定是否保留新窗口。

## 建议的后续动作

- 覆盖 `hybrid`：先用 `数据/ground_truth.json`（301 条真值）跑 A/B，确认新窗口不引入误判后再放开。
- 同类问题：日期链路写死 `model_variant="server"` 的位置（`date_crop_confirmation.py:41/147/292`、
  `date_crop_line_audits.py:24/177`、`date_crop_regions.py:184/255`、`date_crop_region_output.py:41`）
  在方案路径下会静默返回 `[]`，可参照 `seal_audit_policy` 补一个日期侧策略解析。
- 考虑给 `find_receipt_date` 的窗口边界加上显式的越界告警，避免以后再出现"读对了却整窗丢弃"
  这种只能靠翻 `date_ocr_texts` 才能发现的静默失败。
