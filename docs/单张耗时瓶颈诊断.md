诊断日期：2026-09-18
样本：`数据/7266220440.jpg`、`数据/7266220437.jpg`
工具：`tmp/trace_ocr_calls.py`、`tmp/bench_page.py`、`tmp/bench_ort.py`、`tmp/bench_best.py`、`tmp/bench_server_ort.py`

## 一、当前 PaddleOCR 的调用方式

### 1.1 入口链路

```
app.py / job_worker
  ├─ 有识别方案 → recognition_config.run_configured()   ← 网页端实际路径
  └─ 无识别方案 → analyzer.analyze()                    ← tools/batch_validate.py、旧结果重跑
        ↓
recognition_config._recognize_stages()   →  四个 stage：fields / products / date / seal
        ↓
DocumentContext.page(backend)  →  execution.recognize_page()   ← 整页 OCR，按 (路径, 后端) 缓存
        ↓
ocr_backends.recognize_text(path, backend=..., stage=...)   ← backend 即「界面上的识别方式 id」
        ↓
recognition_scope.provider_allowed(provider)   ← 请求级白名单闸门
        ↓
paddle_ocr.recognize_text() / recognize_line()  →  PaddleOCR / TextRecognition.predict()
```

### 1.2 模型档位

| 变体 | 检测 / 识别模型 | 后端 id | 用途 |
|---|---|---|---|
| `mobile` | `PP-OCRv5_mobile_det` / `_rec` | `paddle` | 现行默认（`default_backend()`） |
| `server` | `PP-OCRv5_server_det` / `_rec` | `paddle_server` | 整页兜底 + **印章 Server 审计** |
| `v6` | `PP-OCRv6_small_det` / `_rec` | `paddle_v6` | 2026-09-18 新增，可选 |

`MODEL_VARIANTS` / `VARIANT_PROVIDERS` / `LIGHTWEIGHT_VARIANTS` 为单一数据源，配套
`is_paddle_backend()` / `provider_of()` / `variant_of()` / `is_lightweight_backend()` 四个 helper。

### 1.3 关键事实

- **单张图会发起 18～40 次 `pipeline.predict()`**（随文档内容变化）。
- 每一次调用都是**独立的「文本检测 + 文本识别」全流程**——裁剪图也不例外，是从裁剪图上重新跑检测，而不是从整页检测结果里裁。
- `PaddleOCR` / `TextRecognition` 实例按变体缓存（`_PIPELINES` / `_LINE_RECOGNIZERS`），推理用 `_PREDICT_LOCK` 串行化。
- 单张图最多会加载 **3 个变体 × 2 个网络 = 6 个模型**（当 mobile / v6 / server 同时被用到时）。

## 二、时间都花在哪了

### 2.1 顶级耗时拆解（`7266220440.jpg`，后端 `paddle_v6`）

计时埋点在 `execution.py` 的 `measure()`。`page_ocr` **包含**该次调用内的模型冷加载，
因此下表为互不重叠的顶级计时：

| 阶段 | 未配置识别方案（legacy） | 已配置识别方案（plan，网页端） |
|---|---:|---:|
| **整页 OCR**（含首次模型加载） | 19.5s | 19.1s |
| **印章识别** | **22.0s** | 3.7s |
| **日期识别** | 7.1s | 7.1s |
| 其他（字段、二维码、预览） | 0.9s | 0.9s |
| **合计** | **49.5s** | **30.8s** |

其中整页 OCR 的 19.5s = **约 9.4s 冷加载** + 9.7s 真实推理
（`paddle_model_setup` 40 次调用累计 10.6s，95% 是各流水线的首次构建）。

### 2.2 按调用方与模型变体拆解（legacy 路径，40 次调用）

| 变体 | 调用次数 | 累计耗时 | 平均单次 |
|---|---:|---:|---:|
| `server`（PP-OCRv5_server） | 5 | **18.05s** | **3.61s** |
| `v6`（PP-OCRv6_small） | 35 | 17.11s | 0.49s |

| 调用方 | 次数 | 累计 | 说明 |
|---|---:|---:|---|
| `seal_crop_audit.py:40` | 4 | **17.91s** | 印章 Server 审计（4 张裁剪图） |
| `document_context.py:49` | 1 | 9.72s | 整页 1647×2392，77 行 |
| `date_crop_regions.py:25` | 15 | 3.88s | 日期裁剪图（每张重跑检测） |
| `seal_crop_regular.py:157/90/80` | 3 | 3.00s | 印章常规（圆章展开等） |
| `date_crop_regions.py:115` | 15 | 0.42s | 日期小图 |
| `seal_crop_audit.py:36` | 1 | 0.14s | 行识别（server） |
| `field_rules.py:81` | 1 | 0.07s | 字段区裁剪 |

**结论：Server 模型单次调用比 v6 慢 7.4 倍，5 次调用就吃掉了全部推理时间的一半以上。**

### 2.3 为什么会用上 Server 模型

`receipt_ocr/seal_crop_audit.py` 的 `_read_server_audit_evidence()` **硬编码**：

```python
audit_rows = recognize_line(audit_path, model_variant="server")     # L37
audit_rows = recognize_text(audit_path, backend="paddle_server",    # L42
                            min_text_height=0.012)
```

它**不读取用户选择的 backend**。这是刻意的设计——注释写明这是「跨模型路线」，
Server-only 的读数只作审计留证、不得进入匹配，用来防止同一个模型自证。
**不是 bug，但它与「用户选了 paddle_v6」这个意图是脱钩的。**

触发条件是 `seal_crop_routes.py:124-143` 的 `route.should_server_audit`，
完全由「签章要求」这段文本决定：

- 要求串以 `有限公司` / `有限责任公司` / `分公司` 结尾
- 或命中编号服务章、指定章型（score ≥ 0.50）、未识别的彩色章、三星授权店、服务机构等
- 且页面/印章后端都不是 `paddle_server`

命中后 `route.audit_limit` 取 1 或 2 个候选，每个候选生成 4～5 张审计图。

### 2.4 单张耗时 26s ↔ 49s 的差异来源

| 图 | 路径 | 是否命中 Server 审计 | 总耗时 |
|---|---|---|---:|
| 7266220440.jpg | legacy | 是（5 次 server） | 49.5s |
| 7266220440.jpg | plan | 否（0 次 server） | 30.8s |
| 7266220437.jpg | legacy | 否（0 次 server） | 25.8s |

**同一张图，命中与否直接决定 18 秒的差异。这是当前最大的方差来源。**

### 2.5 真实生产数据

来源：`storage/results.db` → `recognition_jobs` 的 `started_at` / `finished_at`（精度到秒）。

- 397 条近期任务：**中位 9.0s，均值 19.8s，p90 61s，max 303s**
- 全部为 `hybrid` + 带识别方案
- **340 条（86%）走远程 API**（`fields`/`date` = 单证通，`seal` = 清瞳 + 单证通）→ 中位 **8s**，几乎不碰本地 Paddle
- **56 条 `fields=paddle`** → 中位 **19s**

所以「感觉一张太久」主要来自两个地方：
1. 用到本地 Paddle 的那批（中位 19s）；
2. **长尾**——p90 已到 61s，个别到 300s（多半是命中 Server 审计 + 首页/续页/多章叠加）。

### 3.3 ONNX 的实施成本

- 首次转换是**一次性**开销（server 约 300s，v6 约 30s）。
- 转换结果落盘缓存，二次加载仅 0.35～0.45s：
  ```
  ~/.paddlex/official_models/PP-OCRv6_small_det_onnx/inference.onnx
  ~/.paddlex/official_models/PP-OCRv6_small_rec_onnx/inference.onnx
  ~/.paddlex/official_models/PP-OCRv5_server_det_onnx/inference.onnx
  ~/.paddlex/official_models/PP-OCRv5_server_rec_onnx/inference.onnx
  ```
  `~/.paddlex` 当前合计 432 MB。
- `TextRecognition`（行识别，日期链路重度依赖）同样支持：加载 0.34s、单行识别 0.02s。
- 改动量极小：`paddle_ocr._pipeline()` 和 `_line_recognizer()` 里各加一个 `engine="onnxruntime"`。

## 六、P0 / P1 实施结果（2026-09-18）

### 6.1 P0：ONNX Runtime 引擎

改动只在 `receipt_ocr/paddle_ocr.py`：

- 新增 `DEFAULT_ENGINE`、`_DISABLED_ENGINES`、`paddle_engine()`、`_engine_kwargs()`。
- `_pipeline()` 与 `_line_recognizer()` 把 `**_engine_kwargs()` 传给 `PaddleOCR(...)` / `TextRecognition(...)`。
- 环境变量 `PADDLE_OCR_ENGINE`：默认 `onnxruntime`；设为 `paddle` / `off` / `cpu` / `0` / `false` / `none` / 空 时回到默认内核；onnxruntime 未安装时静默回落，不影响无该依赖的机器。
- 引擎值变化时自动清空 `_PIPELINES` / `_LINE_RECOGNIZERS`，保证同一进程内切换设置立即生效；设置稳定时不清空，`tools/benchmark_page_inputs.py` 往 `_PIPELINES["mobile"]` 注入的代理仍然有效。

实测（`数据/7266220440.jpg`，整页 1647×2392）：

| 配置 | 冷加载 | 热态整页 |
|---|---:|---:|
| 默认内核 | 2.77s（v5 Mobile）/ 0.40s（v6） | 15.6s（v5 Mobile）/ 9.8s（v6） |
| ONNX Runtime | 0.41s | **1.68s**；加检测限长 1400 后 **1.41s** |

ONNX 首次转换是一次性成本（v6 约 30s、Server 约 300s），落盘在
`~/.paddlex/official_models/{PP-OCRv6_small_det,PP-OCRv6_small_rec,PP-OCRv5_server_det,PP-OCRv5_server_rec}_onnx/`。

### 6.2 P1：审计策略（`SEAL_AUDIT_MODE`）

**先修的是一个正确性缺陷，不是性能问题。** 审计代码写死 `backend="paddle_server"` / `model_variant="server"`，而 `recognition_config` 把每个阶段的授权范围设成 `{所选后端id}`。实测确认：

```
无 scope（legacy）      backend=paddle_server -> 72 行 | recognize_line(server) -> 1 行
scope={'paddle_v6'}     backend=paddle_server ->  0 行 | recognize_line(server) -> 0 行
```

`recognize_text` 在范围不匹配时**按设计静默返回 `[]`**，所以网页端整条审计支路一直是空转：
同一张图在 legacy 路径产出 72 行证据、在 plan 路径产出 0 行，且界面上看不出区别。

新增 `receipt_ocr/seal_audit_policy.py` 作为唯一决策点：

| 模式 | 行为 | 单张印章识别耗时（440 样本，ONNX 下） |
|---|---|---:|
| `auto`（默认） | 已授权时用 Server，否则**显式跳过并记录原因** | 1.21s |
| `server` | 强制 Server 跨模型审计，并把 `paddle_server`+`paddle` 并入印章阶段授权 | 11.31s |
| `local` | 用本地轻量模型复算，不加载 Server；无第二档时不宣称跨模型 | 约 2～4s |
| `off` | 完全跳过 | 1.44s |

`auto` 是刻意保持现状的：无授权范围的 `analyzer.analyze` 仍然执行审计，方案未勾选 Server 的网页端仍然不执行——变的只是「静默」改成「显式且可归因」。

配套改动：

- `seal_crops._apply_seal_audit_plan()` 解析策略，`should_server_audit` 为真但策略拒绝时，往每个印章证据写入 `server_audit_skipped_reason` + `server_audit_mode`。
- `seal_crop_audit._read_server_audit_evidence(audit, route)` 改用 `route.audit_backend` 与 `variant_for_audit_backend()`，不再写字面量。
- `seal_crop_audit_images` 的稳健分带预读改用 `route.audit_band_backend`，且仅在它存在时生成（分带存在的意义是与审计模型构成跨模型对照）。
- `seal_crop_audit` 的 `_shared_long_organization_suffix` 增加 `route.audit_band_backend` 门禁，避免同一模型自证「跨模型共同后缀」。
- 证据里记录实际后端：`server_audit_backend`（真实标签，不再是写死的 Server）、`server_audit_mode`、`server_audit_independent`。
- `recognition_config` 仅在显式 `server` / `local` 模式下放宽印章阶段授权，`auto` 不放宽。
- 新增 `recognition_scope.allowed_providers()` 供策略读取当前授权范围。

### 6.3 一个必须知道的结论

**这条审计支路不是可有可无的兜底。** 在 `数据/7266220440.jpg` 上（真值 `seal_should_match = true`）：

| 模式 | 印章判定 |
|---|---|
| `auto`（未授权，实际等同跳过） | **无法判断**（漏判） |
| `server` | **匹配** ✓ |

`server` 模式下 Server 读出「北京京凌科技有限公司海淀第三分公司三星售后服务专用章」，正是要求章。
所以网页端当前默认（`auto` + 方案未含 Server）在这类浅色/分体章上是**在漏判**。
是否把默认改成 `server` 需要业务侧权衡吞吐与漏判率——`auto` 只是把这件事变得可见，没有替用户做决定。

### 6.4 回归验证（2026-09-18）

**（1）单元测试。** 新增 `tests/test_seal_audit_policy.py`（35 例）：4 种模式的策略解析、`server`/`local` 的授权范围放宽与 `auto` 不放宽、审计后端变体映射、跳过原因落盘、ONNX 引擎选择与回落（含 `PADDLE_OCR_ENGINE=off`、onnxruntime 缺失、引擎切换清缓存）、以及 `/api/ocr-backends` 返回 `engine` / `seal_audit`。与 `tests/test_ocr_backends.py` 合跑 **68 passed**。

**（2）5 样本真值复跑**（legacy 路径 `tools/batch_validate.py --backend paddle_v6 --limit 5`，引擎为 ONNX）：

| 样本 | 日期 | 印章 | 耗时 |
|---|---|---|---:|
| 7266220437.jpg | 匹配 | 匹配 100% | 10.14s |
| 7266220439.jpg | 匹配 | 匹配 100% | 5.45s |
| 7266220440.jpg | **不匹配**（把 01-05 读成 04-05，v6 固有弱点） | 匹配 100% | 14.44s |
| 7266227347.jpg | 未识别 | 匹配 100% | 5.48s |
| 7266274552.jpg | 匹配 | 匹配 85% | 4.94s |

平均 8.09s（改动前同口径 ONNX 平均 10.13s）。这 5 张真值 `seal_should_match` 均为 `true`，**印章结论 5/5 与改动前一致**；日期 4/5，唯一不符的仍是 v6 自身的日期弱点，与本次改动无关。legacy 路径走 `auto` 且授权范围不受限，审计照常执行——这正好验证了「`auto` 保持原有行为」这一设计约束。

**（3）完整套件里的"假失败"——务必不要重复排查。** 跑 `pytest tests` 时会在后段出现成片的 `SystemExit: 1`，报头形如：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn",...}
```

这是**沙箱的批量删除守卫**在同一个 turn 内累计到 50 次删除后拒绝后续 `unlink`，与业务代码无关：它命中 `tmp_path` 清理和 `app.py:393 _cleanup_cancelled_upload` 这类正常的临时文件删除，且在真正删除**之前**就抛出。特征是

- 同一份日志里 `SAFE_DELETE` 出现几十次，全部指向 `sitecustomize.py` 的 `_check_bulk_delete_guard`；
- 受影响的用例名与删除行为一一对应（`test_*_deletes_*`、`test_*_upload_*`、以及一切用 `tmp_path` 的用例）。

判定方法与本次实测：把守卫的计数状态指到一个独立目录、只跑受影响的模块，**439 passed / 0 failed / 0 error**；新增用例单跑 **68 passed**。改动前后的整轮对比也一致——改动前 `2 failed, 916 passed`，改动后中途一次 `2 failed, 950 passed`（`SAFE_DELETE` 出现 0 次），说明新增用例本身没有问题。

## 五、注意事项

- 分析前必须先理解计时语义：`page_ocr` **包含**模型冷加载；`paddle_model_setup` 是 40 次调用的**累计值**（含全部首次加载）。**这些数字不能直接相加**。
- `measure('paddle_queue_wait')` 恒为 0——单线程串行，锁无争用。
- ONNX 已作为默认引擎生效（`PADDLE_OCR_ENGINE=onnxruntime`）。判断依据是整页 + 印章裁剪的逐字一致、以及 5 样本真值复跑无回退（见 6.4）；**尚未跑满 301 张真值全集**，若要更硬的证据应补一次全量 A/B。回退只需 `export PADDLE_OCR_ENGINE=off`。
- 生产数据的时间戳精度只到秒，2～3s 的差异看不出来，只适合看宏观分布。
- **同类的静默空转问题在日期链路仍然存在**（本次未改）：`date_crop_confirmation.py:41/147/292`、
  `date_crop_line_audits.py:24/177`、`date_crop_regions.py:184/255`、`date_crop_region_output.py:41`
  都写死 `recognize_line(model_variant="server")` 或 `backend="paddle_server"`，由
