# 后台任务队列与恢复

更新日期：2026-09-11

## 用户流程

选择图片后，页面先保存本批次的逐文件清单，再把图片导入本地。新导入的图片保存为“待开始”，此时不执行识别，也不向远程识别服务发送图片。导入期间页面提示保持打开，导入完成后可以刷新或关闭浏览器。

用户在工作台点击“开始识别”，才把当前导入日期内已经导入完成的待开始项提交到后台队列；提交时固定这些任务 ID，不会启动其他日期或之后新导入的回单。若识别方案包含远程服务，页面在开始前显示用途提示，点击开始后才允许相应识别流程执行。无需再处理浏览器确认弹窗。

进度页面自动查询后台状态，重新打开后仍可查看。选择的进度日期保存在本地浏览器中。

| 状态 | 含义和可执行操作 |
|---|---|
| 待上传 | 只有任务清单，尚未收到完整图片；可以通过“补传图片”重新选择对应文件 |
| 上传中 | 当前页面正在传输图片，此时关闭页面可能中断尚未传完的文件 |
| 待开始 | 图片已保存在本地，等待用户点击“开始识别”；刷新、重启服务或点击“继续识别”都不会自动释放 |
| 等待识别 | 用户已经点击开始，正在等待后台执行；全局暂停时仍保留在队列中 |
| 识别中 | 后台正在处理此图片，关闭浏览器不会停止执行 |
| 已完成 | 已保存识别结果；结果可能通过、不通过或需要人工复核 |
| 失败 | 整次识别执行异常，可点击“重试此项”；其他任务继续执行 |
| 已取消 | 例如原记录在重新识别期间被删除，不再覆盖或重建该记录 |

未上传的文件不能在浏览器关闭后凭空恢复；这些任务会保持“待上传”，不会被统计为识别失败，也不会阻止已经开始的图片继续处理。补传核对原任务文件名，防止把另一张图片标成原文件。新导入任务补传成功后仍是“待开始”，需要明确点击开始。

单张重新识别和批量重新识别也进入后台队列，提交后立即返回进度页面。同一记录已有等待或执行中的重试时，不重复创建。进度按独立任务项及记录身份展示，同名但不同的上传不会仅因名称相同而互相覆盖；回单记录列表与分页合并仍沿用原规则。

## 执行与恢复

- `recognition_jobs` 表保存每项的文件引用、状态、识别配置、时间、执行次数及结果关联。`start_requested` 保存该任务是否已获准开始；新导入项为 `0`，点击开始后为 `1`。
- 为兼容已有数据库，旧任务迁移后的 `start_requested` 默认为 `1`，保留之前已授权队列的执行行为。新导入项在内部使用 `queued` 保存上传完成状态，对外仅在已授权时显示 `queued`；尚未授权时显示 `ready`。任务和全局统计分别返回 `ready` 与 `queued` 数量。
- 消费者只领取 `status='queued' AND start_requested=1` 的任务；数据库触发器还会阻止未开始的任务被改为 `running`。服务重启恢复、页面刷新和全局继续不会修改新导入项的开始授权。
- 识别配置在提交时保存，后续修改页面设置不会改变排队中的任务。
- `batch_tasks.execution_mode` 区分旧同步任务和新后台任务。原有同步接口保留给已有验收脚本；网页使用后台模式。
- 每个数据库由一个持有本地进程文件锁的后台工作线程执行。多个服务进程不会同时消费同一个后台队列。Paddle 原有预测锁保留；已配置的清瞳请求仍在单张流程内与本地识别重叠执行。
- 结果保存、重试历史、分页关联、任务完成状态和进度更新在同一个 SQLite 事务中提交。中间异常会一起回滚，避免重启后重复插入结果或遗漏分页关系。
- 执行进程意外退出后，下一次启动服务的队列工作线程重新领取已授权的未完成项；待开始项继续等待用户操作。任务的原始图片必须仍在本地。
- 识别中断后可能重新执行 OCR 或清瞳请求；这里保证的是已完成结果不会重复入库，并不宣称外部接口在崩溃前后只调用一次。
- 重新识别失败时保留原结果。排队或执行期间若发生人工修改，则拒绝用旧输入覆盖新修改；记录被删除时不重新创建它。

后台执行依赖本地服务进程运行。关闭浏览器与停止本地服务不同；服务停止时任务暂停，重新启动后恢复已授权任务，待开始任务保持待开始。第一次加载新版时会自动创建新表及列，无需迁移现有结果 JSON。全局“继续识别”只恢复已经开始的队列，不代替“开始识别”；全局暂停期间点击开始，则相应任务等待继续。

报告导出和批量复核命令只初始化存储，不启动识别工作线程，避免查看或导出报告时意外接手后台任务。

## 接口与代码边界

`receipt_ocr/job_store.py` 负责持久化及事务，`job_worker.py` 负责独占执行与恢复，`job_service.py` 负责在没有网页请求上下文的情况下调用识别流程。

网页使用以下接口：

- `POST /api/tasks`：传入 `background: true`、图片清单和配置，创建新导入任务，返回各项的 `start_requested: false`。
- `POST /api/jobs/<id>/upload`：导入本地并立即返回，新任务状态为 `ready`，不唤醒识别；重复提交同一任务项不会重复保存或识别。
- `POST /api/jobs/start`：传入 `{ "ids": ["任务项 ID", "..."] }`，在一个事务内核验并授权这些已导入项。单次最多 5,000 项；更大范围按点击时固定的 ID 清单分批提交。返回 `started`、`items` 和 `control`；重复开始已授权项不会再次识别。包含不存在或尚未导入完成项的请求整体拒绝，不会部分授权。
- `GET /api/queue?import_date=YYYY-MM-DD`：读取当天的轻量任务状态。
- `GET /api/tasks/<id>`：读取某批次的逐项状态和统计。
- `GET /api/queue/control`：读取全局暂停状态及运行、已授权排队、待开始、待上传数量；`POST /api/queue/control` 传入布尔值 `paused`，只暂停或继续已授权队列。
- `POST /api/jobs/<id>/retry`：单独重试失败项。
- 原单张和批量重新识别接口传入 `background: true` 后，创建后台重试任务。

结果中的 `queue` 保存任务 ID、执行次数、上传时间、开始时间和排队秒数。第一轮加入的 `processing_seconds` 和 `processing_timings` 继续记录实际识别阶段，与队列等待区分。

页面通常每 2 秒查询轻量状态，隐藏页面时放宽到 5 秒。完成状态改变或手动刷新时读取完整结果，其余情况下复用最多 30 秒的结果缓存。未变化的列表不会反复重建，保留按钮焦点及正在进行的点击。

## 文件夹递归导入（2026-09-10）

- “选择文件夹”保留浏览器返回的完整相对路径，包含所有层级子文件夹；拖入目录通过目录项逐层遍历，并持续读取目录分批结果，直到返回空批次。
- 支持 JPG/JPEG、PNG、BMP、WEBP，按扩展名与后端保持一致；其他文件跳过并计数，读取失败明确提示。路径相同的文件名在不同子目录中分别建任务、分别保存，不覆盖。
- 扫描期间显示已发现文件数并阻止重复导入。超过每批 5,000 张时自动分批上传；上传并发仍为 2，识别仍由后台队列处理。
- 文件名或订单号的统一前缀搜索同时匹配图片基础文件名，带目录路径的 `7` 开头图片仍可搜索。
- 44 项相关回归通过，覆盖目录超过 100 个子项时的后续批次、多层目录、同名图片、非图片跳过、读取异常、大批次拆分、独立存储与前缀查询。
- 浏览器在隔离数据库中实际选择四层目录，4 张支持图片全部入队，3 张同名图片分别保留，文本文件跳过；另通过目录拖拽事件验证根目录和子目录图片均成功上传。

## 全局暂停与继续（2026-09-10）

- 工作台右上角新增“暂停识别 / 继续识别”，作用于所有日期的识别队列，日期切换仅改变列表范围。
- 暂停为安全停止领取：正在识别的一张完成并保存后停下，其余图片保留排队；显示“暂停中”直到运行数归零。继续只领取未完成的排队任务，不重新执行已完成项。
- 暂停状态保存在 SQLite `queue_control` 中，刷新页面和服务重启后均保留。暂停期间仍可导入、补传、重试入队和人工复核，新任务等待继续。
- `GET /api/queue/control` 返回暂停标志、全局运行/排队/待上传数量及状态；`POST /api/queue/control` 接收严格布尔值 `paused`。继续时唤醒消费者。
- 暂停变更与任务领取都使用写事务串行化；数据库触发器同时阻止旧版本消费者在暂停状态下领取新任务。正在运行任务的结果提交不受影响。
- 自动化覆盖当前结果保存、阻止下一次领取、重建存储实例后保留暂停、重启恢复任务仍暂停、暂停接受上传、继续只领取剩余任务及接口参数校验。隔离浏览器验证暂停、刷新后继续按钮状态和服务端控制状态。
- 本次按用户指令将真实队列暂停；当时在途的一张完成保存后安全重启服务加载控制功能。验证时剩余 902 张排队、0 张运行。
