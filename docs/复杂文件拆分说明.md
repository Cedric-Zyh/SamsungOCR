# 复杂文件拆分说明

项目按职责拆分解析、日期识别、印章识别、任务执行、Web 和前端代码。识别规则、阈值、证据格式和页面接口保持稳定；主要收益是让每层只依赖明确的下层边界。

下表描述当前代码边界；旧入口文件已移除，运行时只通过这些新边界组合。

| 当前边界 | 实现位置 |
| --- | --- |
| 领域解析 | `receipt_ocr/domain/parsing/` |
| 应用编排与识别入口 | `receipt_ocr/application/` |
| 识别阶段编排 | `receipt_ocr/stages/` |
| 日期与印章识别 | `receipt_ocr/recognition/date/`、`receipt_ocr/recognition/seal/` |
| 任务执行 | `receipt_ocr/jobs/` |
| 持久化 | `receipt_ocr/persistence/` |
| Web 组合 | `receipt_ocr/web/application.py` |
| Web 路由注册 | `receipt_ocr/web/routes.py` |
| 前端组合入口 | `static/modules/shell/application.mjs` |
| 分析与运维工具 | `tools/analysis/{date,seal,operations}/` |

## 解析

解析实现统一位于 `receipt_ocr/domain/parsing/`，具体职责分别位于：

- `parsing_text.py`、`parsing_constants.py`：文本规范化与原有常量、业务主数据。
- `parsing_fields.py`：字段提取、纠错调度和字段可信度。
- `field_identity.py`、`field_requirements.py`：客户身份、地址、签章要求等顺序纠错规则。
- `parsing_products.py`：商品表格解析。
- `parsing_dates.py`：日期解析与比较。
- `parsing_seals.py`：印章文本匹配。

原 `repair_contextual_fields` 已拆为 11 组有明确参数的规则，入口按原顺序调用。字段、商品和印章规则直接依赖领域解析包。

## 日期

日期功能对外只暴露 `receipt_ocr/recognition/date/` 下的稳定边界，`stages/date.py` 只负责阶段编排：

- `api.py`：应用层唯一识别入口 `recognize_receipt_date`。
- `workflow.py`：跨步骤流程编排。
- `crops.py`：日期裁剪生命周期、区域和槽位采集。
- `evidence.py`：OCR 片段、图像派生、跨模型与业务证据。
- `decision.py`：共识、日期选择和可信度决策。
- `audit.py`：低置信度和补充审计。
- `slots.py`：日期槽位探测。

历史拆分产生的实现模块统一收纳在 `date/_internal/`，只允许上述边界和日期包内部互相访问；应用层、测试和分析工具不再直接导入这些实现文件。日期判断的规则优先级、提前结束条件、补充模型范围以及仅供人工查看的证据限制均保持不变。

## 印章识别

印章功能对外只暴露 `receipt_ocr/recognition/seal/` 下的稳定边界，`stages/seal.py` 只负责阶段编排：

- `api.py`：印章 API 客户端和识别模式。
- `workflow.py`：本地印章识别、区域调度和阶段执行适配。
- `evidence.py`：章区、审计图像和证据对象。
- `decision.py`：印章文本、公司和业务章决策规则。
- `audit.py`：二次审计和证据路由。
- `policy.py`：本地通道、提供方和审计策略。
- `orientation.py`：印章方向处理。
- `providers/`：清瞳 API、区域映射和预览适配。
- `reference/`：参考样本匹配及其几何、门槛、共识和置信度实现。

历史碎片实现统一收纳在 `seal/_internal/`；应用层、测试和分析工具通过上述边界访问印章能力。清瞳仅 API、清瞳 + 本地、纯本地三种模式的调用顺序、区域证据和页面接口保持不变。

## 共享识别契约

`receipt_ocr/recognition/shared/` 存放日期与印章共同使用的轻量契约，包括 `TextObservation`、`StageRequest`、`SealRegion` 及其文本序列化工具。共享包不承载业务规则，避免两个垂直切片互相穿透。

## 印章参考匹配

`recognition/seal/reference/matcher.py` 负责参考样本管理和 `SealReferenceMatcher` 入口，并通过 `reference/` 边界组织已有规则函数和常量。实现拆为：

- `reference/geometry.py`：OpenCV 实例、图像表示、缓存、局部特征与颜色比较。
- `reference/constants.py`：原校准阈值及供结果展示的阈值说明。
- `reference/gates.py`：单条证据的匹配条件和排序。
- `reference/consensus.py`：独立参考文件之间的一致性判断。
- `reference/decision.py`：按原优先级选择匹配路径并组装结果。
- `reference/confidence.py`：各匹配路径的可信度计算与上限。

## 分析工具

分析脚本按关注点归档到 `tools/analysis/date/`、`tools/analysis/seal/` 和 `tools/analysis/operations/`。每个脚本都从项目根目录解析导入路径，因此既可以用 `python -m tools.analysis...` 调用，也可以直接执行文件；脚本之间只通过新包路径共享分析函数。

## 前端

`static/app.js` 仅加载并初始化应用。`static/modules/shell/application.mjs` 显式组装控制器、安排初始化和轮询，各控制器通过参数和回调连接。

模块分别管理导入、识别设置、记录列表、复核编辑、复核证据、复核队列、工作台、统计和导航。`state.mjs` 按业务区域划分状态，`api.mjs` 与 `ui.mjs` 承接公共能力。

拆分保留分页与选中项、未保存编辑保护、复核版本检查、异步请求先后顺序保护、后台刷新策略和 HTML 转义。行为测试直接加载实际前端模块，不再从源码中截取函数。

## 维护约定

- 修改规则时定位到对应实现模块；应用层负责编排，领域层负责规则，基础设施层负责外部副作用。
- 顺序规则的前后位置属于业务行为，不能为了整理代码随意交换。
- 新增跨步骤状态需声明明确字段，不通过动态变量转发隐藏依赖。
- 拆分本身不代表 OCR 模型推理会更快，性能改动应另行测量。

## 验证记录

- 所有 Python 文件通过语法解析，`pytest --collect-only -q` 可收集当前测试集，未出现旧模块导入错误。
- 运行时、应用初始化、数据库、任务队列、复核接口和前端模块均已按新边界完成定向回归。
- 前端测试现在直接加载 `static/modules/{core,imports,records,progress,review,shell}` 下的实际模块；`static/app.js` 只加载 shell 组合根。
- 全量测试仍包含项目既有的模型默认值、印章提供方和前端设置断言差异；这些失败来自本轮之前的识别配置改动，需单独校准，不作为旧目录迁移的兼容层保留。
- 差异检查使用当前工作树和隔离测试输入，未对业务回单重新识别；本轮未进行真实新样本验收和大规模性能测试。
